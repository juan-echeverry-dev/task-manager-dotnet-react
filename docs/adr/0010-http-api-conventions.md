# 0010. HTTP API conventions

- Status: Accepted
- Date: 2026-11-17

## Context

Endpoints need consistent verbs, status codes, error format, and discoverable documentation.

## Decision

- **Controllers** (`[ApiController]`), one per module resource, thin: bind input, call the
  handler, map the `Result` to an HTTP response.
- Routes under `/api/...`; resource-oriented verbs (`GET`, `POST`, `PUT`, `DELETE`);
  `201 Created` with `Location` on creation, `204 No Content` on deletion.
- **Errors are RFC 9457 Problem Details** everywhere (`AddProblemDetails`,
  `UseExceptionHandler`, `UseStatusCodePages`); validation errors include an `errors` map.
- **OpenAPI** document generated by `Microsoft.AspNetCore.OpenApi` at `/openapi/v1.json`,
  browsable with **Scalar** at `/scalar/v1`, both in Development only.
- **`GET /health`** (anonymous) reports API and database health.

## Alternatives considered

- **Minimal APIs**: a natural fit for vertical slices, but controllers map more directly to the
  "ASP.NET MVC / Web API" requirement and are familiar to reviewers.
- **Swashbuckle / Swagger UI**: no longer part of the ASP.NET Core templates since .NET 9.

## Consequences

- One error shape for the frontend to handle (`ApiError` in `src/shared/api/http-client.ts`).
- API documentation stays in sync with the code without hand-written specs.
